# Lab 2 UI Specification

## 1. Purpose

This document defines the user-interface specification for the Lab 2 Requester-facing TokTickIT application.

The UI must provide a consistent and reusable **Zen Green** design system for:

* Development Requester Selection
* Application navigation
* Create Ticket
* My Tickets
* Requester Ticket Detail
* Attachment management
* Validation
* Loading states
* Success states
* Empty states
* No-results states
* Failure states
* Responsive desktop, tablet, and mobile layouts

The Development Requester selector is a temporary Lab 2 testing mechanism and must not be presented as real authentication.

---

# 2. Design Principles

The Lab 2 UI shall follow these principles:

1. **Consistent**
   The same colors, spacing, labels, controls, badges, buttons, validation patterns, and feedback states shall be reused across screens.

2. **Clear**
   Requesters shall be able to understand which values are editable, which are generated by the system, and what action should be taken next.

3. **Responsive**
   The application shall remain usable on desktop, tablet, and mobile screens without unintended horizontal page scrolling.

4. **Accessible**
   Controls shall support keyboard interaction, visible focus states, readable labels, and non-color-only feedback.

5. **Safe**
   Failure messages shall be understandable without displaying internal server information, stack traces, database details, or file-system paths.

6. **Reusable**
   Components created in Lab 2 should be reusable by later TokTickIT screens.

# 5. Spacing and Layout

Use a consistent spacing scale.

Recommended scale:

```text
4 px
8 px
12 px
16 px
24 px
32 px
48 px
```

General rules:

* Minimum 8 px between a label and its control.
* Minimum 16 px between related form fields.
* Minimum 24 px between major form sections.
* Cards use approximately 20–24 px internal padding on desktop.
* Mobile cards may use 16 px padding.
* Main page content shall use a sensible maximum width of approximately 1200–1280 px.
* Main content shall remain horizontally centered on large displays.

---

# 6. Surfaces and Cards

Cards shall use:

* White background
* Subtle neutral border
* Small border radius
* Restrained shadow
* Clear visual separation from the page background

Recommended:

```css
background: #FFFFFF;
border: 1px solid #D7E0DB;
border-radius: 8px;
```

Heavy shadows, gradients, or decorative visual effects shall not distract from the support-ticket workflow.

The shared application shell shall contain:

* My Tickets navigation
* Create Ticket navigation

* Change Requester shall remain accessible.

# 8. Development Requester Selection Screen

## 8.1 Purpose

This screen establishes the temporary Requester testing context before the user enters Requester-specific screens.

It must clearly state that it is not authentication.

## 8.2 Required Elements

The screen shall contain:

* TokTickIT title
* Development Requester Selection heading
* Short explanatory text
* Development Requester dropdown
* Continue button
* Loading state
* Empty state
* API failure state

Recommended explanation:

> Select a Development Requester to test requester-specific ticket behavior. This is not a login screen. Authentication and role-based access will be introduced in Lab 3.

## 8.3 Requester Dropdown

Label:

```text
Development Requester *
```

The dropdown shall:

* contain only active Requesters
* initially display a placeholder
* support keyboard selection
* show a visible focus state

Example placeholder:

```text
Select a requester
```

Inactive Requesters shall not be displayed.

## 8.4 Continue Button

The Continue button shall be:

* Primary Green
* clearly labelled `Continue`
* disabled when no valid Requester is selected

## 8.5 Loading State

While Requesters are loading:

* requester dropdown is disabled
* Continue is disabled
* loading indicator or skeleton is displayed
* text shall communicate that Requesters are loading

Example:

```text
Loading Development Requesters…
```

## 8.6 Empty State

If no active Requesters exist:

```text
No active Development Requesters are available.
```

Continue shall remain disabled.

## 8.7 Failure State

If the Requester API fails:

* show a safe error callout
* do not display technical implementation details
* provide Retry if practical

Example:

```text
Development Requesters could not be loaded. Please try again.
```

# 9. Form Controls

All forms shall use consistent controls.

## 9.1 Labels

Labels appear above controls.

Required fields shall use:

```text
Ticket Summary *
```

The red asterisk indicates that the field is required but does not replace a validation message.

## 9.2 Editable Fields

Editable fields shall use:

* white background
* neutral border
* dark text
* clearly visible focus indicator

## 9.3 Read-only Fields

Read-only fields shall use:

* gray-green background
* neutral border
* readable text
* no appearance suggesting they can be edited

Read-only fields shall not rely only on disabled opacity because their values must remain readable.

## 9.4 Invalid Fields

Invalid fields shall use:

* dark-red border
* validation message below the field
* appropriate accessibility error association

Example:

```text
Ticket Summary *
[                                    ]
Ticket Summary must contain at least 5 characters.
```

## 9.5 Focus State

Keyboard-focused controls shall retain a visible focus ring.

Focus indicators shall not be removed with CSS unless replaced by an equally visible alternative.

## 9.6 Disabled State

Disabled controls shall:

* appear visually distinct
* not respond to pointer interaction
* not be keyboard-activatable

---

# 10. Button Hierarchy

## 10.1 Primary Button

Used for the main action.

Examples:

* Continue
* Submit Ticket
* Upload Attachment

Style:

* Primary Green background
* White text
* clear hover state
* visible keyboard focus

## 10.2 Secondary Button

Used for supporting actions.

Examples:

* Cancel
* Clear Filters
* Back to My Tickets

Style:

* White or pale background
* Green border/text

## 10.3 Tertiary Button

Used for low-emphasis actions.

Examples:

* View
* Download

May appear as a text-style button or link while maintaining accessible hit area and focus state.

## 10.4 Destructive Button

Used for soft-removing an Attachment.

Example:

```text
Remove Attachment
```

Destructive styling shall use dark red rather than green.

## 10.5 Disabled Button

Disabled buttons shall have:

* neutral background
* muted text
* disabled cursor
* no hover interaction

## 10.6 Busy Button

When an action is being processed:

```text
Submitting…
```

or:

```text
Uploading…
```

The button shall:

* remain visibly busy
* become disabled
* prevent duplicate activation

# 38. Responsive Requirements

## 38.1 Desktop — 992 px and Above

* Multi-column form layout where practical.
* Main content centered.
* Sensible maximum width.
* My Tickets uses desktop table.
* Ticket Detail may use multiple columns for metadata.
* Description uses full or wide column.
* Attachment filenames remain readable.

## 38.2 Tablet — 768 to 991 px

* Two-column layout where practical.
* Summary and Description receive enough width.
* Filter controls may wrap.
* Ticket table may reduce less-important visual spacing while remaining readable.
* Ticket Detail may reduce from several columns to two.

## 38.3 Mobile — Below 768 px

* Form fields stack vertically.
* My Tickets uses cards.
* Ticket Detail fields stack.
* Buttons remain touch-friendly.
* Filter controls stack or wrap clearly.
* No horizontal page scrolling.
* Long filenames wrap or truncate safely without breaking layout.

## 38.4 All Viewports

There shall be:

* no clipped labels
* no overlapping validation messages
* no hidden actions
* no unreadable Attachment filenames
* no unintended horizontal scrolling

# 51. UI Acceptance

The Lab 2 UI is considered conformant when:

* all required Requester-facing screens exist
* the Zen Green visual system is consistently applied
* all required screen states are implemented
* editable and read-only information are clearly distinguishable
* validation appears near affected fields
* Requester context is always understandable
* Attachment states are clearly represented
* desktop, tablet, and mobile layouts meet the responsive requirements
* accessibility rules are followed
* required automated UI checks pass
* required Playwright screenshots are produced
* the completed visual inspection checklist passes
